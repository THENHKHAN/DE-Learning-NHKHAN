Key RDD properties
🔒 Immutable
Never modified in-place. Every transformation returns a new RDD. Enables safe parallel reads.
🌐 Distributed
Partitions live on different machines. All nodes work simultaneously — true parallelism.
♻️ Resilient
If a node fails, Spark re-computes lost partitions using the DAG lineage graph.
Lazy evaluation — nothing runs until an action is called
Transformations (lazy)
Build a plan — no data moves yet.
map() filter() flatMap() groupByKey() reduceByKey()
Actions (trigger execution)
Force Spark to evaluate the plan.
collect() count() saveAsTextFile() take(n)
E-commerce example — lineage chain
1. Raw RDD
sc.textFile("logs.txt") — 100M rows, 4 partitions
↓ filter()
2. Failed transactions RDD
filter(lambda r: r['status'] == 'FAILED') — 2M rows remain
↓ map()
3. (user_id, amount) RDD
map(lambda r: (r['user_id'], r['amount'])) — extract key-value pairs
↓ reduceByKey()
4. Total loss per user RDD
reduceByKey(lambda a, b: a + b) — aggregated per user
↓ count() ← ACTION fires here
Result: 45,231 affected users
Spark now executes all steps above across all 4 nodes in parallel

How lineage makes resilience possible
DAG Lineage
Spark stores every transformation step (the "recipe"). It never stores all intermediate data — just the plan to recreate it.
Re-computation
When P2 is lost, Spark re-reads only the source rows 50–74M and re-applies the same transformations — on any surviving node.
Python list vs RDD — the resilience difference
Python list
Stored in one process's RAM. If the process dies → all data is gone. No recovery.
RDD
Spread across nodes + lineage tracked. One node dies → recompute just that partition. Job continues.
